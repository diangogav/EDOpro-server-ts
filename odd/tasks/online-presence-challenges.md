# Online presence and direct challenges

Objective: every visitor of the web client (guests included) appears in a live "online" list with their status, and any player can challenge another directly; an accepted challenge puts both in a private duel room.
Branches: `feat/online-presence` in `EDOpro-server-ts` and in `evolution-card-game`. Delivery strategy: `ask-on-risk`; the client deploys on merge, so it must stay harmless against a server that does not speak presence yet.
Test runner: server `pnpm test <path>`, `pnpm lint`; client `npx vitest run <files>`, `npm run typecheck`, `npm run check:svelte`, `npm run build`.

## Specs

- **S1 — Why.** User: "creo que pega mucho que ves a la gente online en una lista y puedes retarla". Today the client's "online" sidebar only lists players already inside a room (`evolution-card-game/src/features/duel/ui/RoomBrowserScreen.svelte:149`) and clicking a name joins that room; nobody browsing menus is visible and there is no challenge.
- **S2 — Where it lives.** User: "vamos con el server". Presence rides on the existing room-list WebSocket (`src/web-socket-server/WebSocketSingleton.ts`, `WEBSOCKET_PORT`), the one `evolutionygo-web-ranking` consumes (`src/components/RoomsWebSocketListener.tsx`). The presence logic lives in its own module (`src/presence/`), separate from the room broadcast, so it can move to `evolution-api` later without changing the client protocol.
- **S3 — Guests included.** Asked "¿los invitados también aparecen en la lista y se les puede retar, o solo cuentas logueadas?"; user answered "si". Guests join with a name and avatar; signed-in players identify with a game ticket from `evolution-api` (`POST /game-tickets`, consumed like `HandshakeTicketAuthenticator` does), one fresh ticket per connection.
- **S4 — Who gets presence.** Only sockets that sent `HELLO` appear in the list and receive presence messages. Anonymous sockets (web ranking viewers) keep receiving exactly what they receive today and never see player names.
- **S5 — Status.** Each online player shows `free`, `searching` or `in-duel`. For signed-in players the server derives it from its own state (matchmaking pool by userId, seated sockets' `resolvedUserId`). Assumption: guests report their own status through a presence message, since a guest's presence socket and duel socket cannot be linked server-side.
- **S6 — Online/offline.** The list arrives once as a snapshot and then as deltas (joined, left, status changed). A closed socket leaves the list immediately; a ws ping every ~25 s drops dead connections. A server restart empties the list and clients reconnect on their own.
- **S7 — Challenges.** A player sends a challenge to someone in the list; the target sees it and accepts or declines; on accept the server creates a private, unlisted room and sends both players the join command, and the client joins it through the normal duel socket. Reserved duels (`rv#<id>`) need userIds, so the challenge room is a private room with a generated password, which works for guests too.
- **S8 — The web ranking does not change.** `GET-ROOMS`, `ADD-ROOM`, `UPDATE-ROOM` and `REMOVE-ROOM` keep their shape and audience; presence only adds new actions. A test pins the existing messages. Risk: item 3 (socket consumed by another system).

- **S9 — One list, formats per player.** User asked "deberia haber una lista por formato? o cada jugador deberia listar que formatos juega haciendo una seleccion en la web?"; accepted proposal: a single list of everyone online, each entry shows the formats that player plays, with format filter chips (no filter = everyone). `HELLO` carries the player's formats and a later message can update them. A challenge offers only the formats both players share; with none in common the challenge button is disabled with the reason.
- **S10 — Formats are an account preference.** User: "en la cuenta, para que siga entre dispositivos". Signed-in players' formats are stored in their account in `evolution-api` (read/write endpoints, new storage through `evolution-types`); guests keep them in the browser. It is one preference with two uses: it replaces the rival alert's browser-only "followed formats" (`evolution-card-game/src/features/settings/application/followedFormats.ts`, ranked formats only) and covers casual formats too. User: "haremos que el usuario seleccione los formatos en sus preferencias incluso los ya registrados, debemos dise;ar ese flujo despues ... pero no deduzcamos nada". Nothing is inferred: no formats from decks, no upload of an existing browser choice; every player, existing accounts included, picks their formats explicitly. The selection flow is designed later (open decision).

- **S11 — Format catalogue.** User: "agrega todos los formatos casuales también". The catalogue is the create-room format list of the client (`evolution-card-game/src/features/lobby/domain/roomCommand.ts` `FORMAT_OPTIONS` + `SPEED_DUEL_FORMAT`): `tcg`, `ocg`, `edison`, `goat`, `jtp`, `jtp-adv-2007-03`, `genesys`, `rush`, `pre`, `speed`. The same ids are stored in the account, sent in `HELLO`, and used to build the challenge room with each format's existing command token. The rival alert keeps reading only the ranked ones (`tcg`, `jtp`, `edison`, `genesys`) from the same preference. `speed` is offered only where the client offers Speed Duel rooms (`roomFormatOptions`).
- **S12 — One duel per challenge.** User: "1 sols partida". A challenge room is always best-of-1 (single); there is no match option in the challenge.
- **S13 — No challenges to a player in a duel.** User: "si, desactivado mientras está en duelo". While a player's status is `in-duel` the challenge button shows "En duelo" disabled and turns on when they are free again; nothing is queued for them. The server rejects a challenge to an `in-duel` player as well, so a stale client cannot get one through.
- **S14 — Players searching can be challenged.** User: "si, si acepta que salga de la cola". A player in the matchmaking queue can receive challenges; accepting removes them from the queue and sends them to the challenge duel; declining leaves them searching. Acceptance: if the queue pairs them before they accept, the challenge fails for both with a clear reason and nobody ends up in two duels; the challenger, if they are the one searching, also leaves the queue when the challenge is accepted.
- **S15 — Expiry and anti-spam.** User: "si, esos valores están bien", accepting: a challenge expires after **30 s** without an answer; a challenger has **one pending challenge at a time**; after a decline the same challenger cannot challenge that player again for **2 minutes**; each player can **mute challenges** (they stay in the list with the challenge button disabled). The server enforces all four; the client only reflects them.
- **S16 — Ranked or casual.** User: "los retos deberian ser rank si son dos cuentas con login no? y si al menos uno es casual, cuenta como casual" and "revisa bien el server, todos los formatos pueden contar para el rank". Verified: `RoomLeague.determine` (`src/shared/room/admission/domain/RoomLeague.ts:33-47`) ignores the format, and `evaluateRatingEligibility` (`src/shared/stats/rating/domain/RatingEligibility.ts:29-44`) rates per `banListName`, skipping only unranked, `"N/A"` ban lists and players without an account. Rule: two signed-in players → the challenge room is ranked (both seated with tickets, the same path `TicketJoinStrategy` uses today), in every format except Speed Duel, which is never ranked (`SpeedDuelJoinStrategy.ts:38`); at least one guest → casual (`casual` token). Pre-release has no ban list, so it is probably ranked without a rating change (not checked at runtime).
- **S17 — The challenge says what it is.** User: "si, que muestre si es ranked o casual". The challenge notice shows the queue and the format before accepting, e.g. "Reto ranked · Goat" or "Reto casual · Edison".
- **S18 — Format selection flow.** User: "si, apruebo el flujo así", approving:
  - Settings has one "Mis formatos" section: multi-select chips for the S11 formats with their meta label. It replaces the rival alert's selector (`evolution-card-game/src/features/settings/ui/RivalAlertControls.svelte`).
  - The first time a player opens the online list with no formats chosen, a short sheet asks "¿Qué formatos juegas?" with a "Ahora no" option; existing accounts get the same sheet the first time after release. It is not part of the onboarding tutorial.
  - Pressing challenge with no formats chosen opens that sheet instead of sending a challenge.
  - A player with no formats appears in the list tagged "Sin formatos" and cannot be challenged.
  - The rival alert no longer falls back to the last ranked format played (`followedFormatsStore.svelte.ts:21`): with no formats chosen it stays silent until the player chooses. Accepted behaviour change for existing players.
